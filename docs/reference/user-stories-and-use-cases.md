# Forge User Stories And Use Cases

This document is the working product contract for Forge. It records what a person can
currently use Forge for, which surfaces and API contracts carry each use case, where the
current implementation is limited, and what evidence is required before an improvement is
kept.

It is intentionally broader than project management. Forge covers structured memory,
planning and execution, calendar and Life Events, notes and KarpaWiki, trusted artifacts,
preferences, Psyche, health, movement, Life Force, nutrition, Workbench, agent access,
gamification, iPhone sync, and watchOS commands.

## How To Use This Contract

1. Select one story, including every web, API, native, and adapter surface named by it.
2. Record the current behavior before editing. Include correctness, latency, scrolling,
   responsive layout, theme behavior, accessibility, empty/error states, and data effects.
3. State the concrete gap between the current behavior and the expected result.
4. Improve the smallest coherent end-to-end path. Do not remove an authored feature to
   make a performance or layout test easier to pass.
5. Retest the same scenario and compare it with the baseline. Keep the change only when the
   result is better and no linked story regresses.
6. Add the evidence to the improvement ledger and update the story state.

The inventory is not a claim that every story has received a fresh quality audit. A code
path can exist while its current quality remains unverified.

## Story States

| State                | Meaning                                                                                                                 |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `Needs audit`        | The use case exists, but it has not passed the complete current iteration protocol.                                     |
| `In review`          | A measured baseline or candidate improvement exists, but one or more gates remain.                                      |
| `Verified`           | The current implementation passed the story's functional, visual, responsive, performance, safety, and contract checks. |
| `Limited`            | Part of the intended outcome is unavailable or has a named material constraint.                                         |
| `Externally blocked` | Forge is ready, but a named external service, entitlement, credential, or review process prevents final verification.   |

## Quality Gates

Every verified story must satisfy the gates that apply to it.

| Gate                | Required evidence                                                                                                                                                                                                                                                            |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| User outcome        | A realistic user scenario reaches the stated result without hidden setup, dead controls, or unexplained route knowledge.                                                                                                                                                     |
| Feature retention   | Existing information, animation, imagery, controls, shortcuts, links, and states remain available unless a deliberate product decision deprecates them. Performance work must optimize rendering, queries, caching, or virtualization instead of making the product sparser. |
| Correctness         | Dates, time zones, ownership, status transitions, derived metrics, side effects, retries, and relationship changes match the stored records and domain rules.                                                                                                                |
| Data safety         | Tests use isolated temporary data. Migrations are additive or recoverable. No check deletes or rewrites the operator's live Forge data. Soft-delete and restore behavior is verified where present.                                                                          |
| API contract        | Normal stored entities use shared batch CRUD by default. Action workflows and specialized domains use their published route families. OpenAPI, onboarding, MCP tools, and plugin skills agree.                                                                               |
| Responsive UI       | The complete workflow works at 390 x 844 and a desktop viewport, with no horizontal overflow, clipped text, displaced controls, or touch targets below the local design-system standard.                                                                                     |
| Theme integrity     | Every supported preset and system theme produces matching root/body color schemes, semantic surfaces, readable text, stable images, and correctly repainted maps, graphs, and canvases.                                                                                      |
| Loading             | The first useful route state appears without an artificial delay or blank shell. Expensive secondary data is deferred only when it does not hide the primary outcome. Every measured route records its local cold and warm baseline before a performance change.             |
| Scroll stability    | A down-and-up stress pass has no blank frames, flashes, disappearing content, reflow loops, broken images, or horizontal overflow. Long collections use bounded queries, pagination, or virtualization.                                                                      |
| Accessibility       | Keyboard order, visible focus, names, dialog focus management, reduced motion, contrast, and status announcements are checked for the changed flow.                                                                                                                          |
| Failure handling    | Loading, empty, partial, offline, permission-denied, stale, and server-error states explain what happened and expose a valid recovery action when one exists.                                                                                                                |
| Regression coverage | Focused tests protect the bug or rule, the relevant package suite passes, and the live workflow is checked in the running product.                                                                                                                                           |

## Psyche And Reflection

Psyche flows require active listening. The agent should reflect the user's words, ask only
for missing or unclear information, and may offer a clearly labeled interpretation or
hypothesis for discussion. It must not present an inference as a diagnosis or fact, minimize
functional analysis, or force the user through a field-by-field form.

or detail views.

## Logic Audit Questions

For each story, answer the applicable questions before calling it verified:

- What is the canonical record or read model, and which derived views can become stale?
- Which actor owns the record, which actor performed the mutation, and which scopes apply?
- Which state transitions are valid, idempotent, reversible, or intentionally irreversible?
- Which side effects occur, in what order, and what happens after partial failure or retry?
- Are timestamps stored as instants with source time zones and rendered in the intended zone?
- Can duplicate imports, uploads, commands, calendar projections, or relationships be detected?
- Are list and graph reads bounded for empty, normal, large, and adversarial datasets?
- Does a specialized domain retain one truthful API family across server, OpenAPI,
  onboarding, MCPs, plugins, web, iPhone, and watchOS?
- Does the flow preserve provenance and distinguish user statements, source facts, derived
  values, model proposals, and agent hypotheses?
- Can the user understand, correct, undo, retry, or safely leave the workflow?
- Does the improvement preserve every useful feature and piece of information present in
  the baseline?
