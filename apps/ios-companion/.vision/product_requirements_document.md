# Forge iOS Companion — Product Requirements Document

Forge iOS Companion is the native Apple client for the Forge ecosystem. It pairs to a specific Forge runtime, captures on-device signals that the web app cannot access directly, syncs those signals into Forge, and exposes a small set of high-value native controls for correction, diagnostics, and wrist-first capture.

The current production stack is Swift 5, SwiftUI, MapKit, HealthKit, Core Location, BackgroundTasks, WatchConnectivity, WidgetKit, App Intents, AVFoundation, the repo-owned Rust `forge-companion-iroh` static library exposed to Swift through FFI, and the live Xcode project at `apps/ios-companion/ForgeCompanion.xcodeproj`. The watch app target is a real watchOS SwiftUI application target, while WidgetKit/App Intent widgets live in their separate extension target. Release automation is handled through Fastlane plus the repo scripts under `apps/ios-companion/scripts/`, with TestFlight and App Store delivery driven from the companion subtree.

The core product surfaces are the pairing flow, permission onboarding, the paired Forge shell, the movement life timeline, settings and diagnostics sheets, HealthKit sync controls, and the watchOS command surface. The paired shell embeds the Forge web experience after authentication, while the native overlays expose the tasks that are more trustworthy or faster in native UI than in a web wrapper.

Pairing is Iroh-first. The companion must decode Forge pairing payloads that include the desktop node id, relay hint, one-time pairing token, and ALPN `forge-companion/1`; preserve that transport metadata across normalization and verified-session refreshes; route paired API and WebKit requests through the Rust Iroh/QUIC bridge when the payload is Iroh-backed; and keep known-host/manual HTTP setup available only as an advanced route for LAN, local simulator, or Tailscale workflows.

HealthKit sync must batch workout collection aggressively, pack workout summaries, heart-rate time series, and routes into larger resumable chunks, prefer compressed chunk uploads when Forge advertises support, surface live upload counts and copyable logs, and keep an active manual upload attached to the finite iOS background task window when the app leaves foreground. Normal sync and historical workout import are separate lanes: sleep, vitals, movement, screen time, and recent workouts must be able to complete without waiting for the older one-time workout backfill.

The watchOS command surface must let the user move through Forge entities with the Digital Crown and then swipe horizontally through dense cards inside the selected surface. Required surfaces include Now, Work, Habits, Goals, Today, Health, Movement, Psyche, People, Inbox, and Sync. Habits open a modal for Done/Missed or Resisted/Performed decisions; work cards can start task runs, refresh heartbeats, complete runs, release runs, and move task status; capture cards can store emotion, trigger, routine, prompt, social, place, trip, workout, and note events. The watch must never own canonical domain state: every mutation is queued locally, relayed through WatchConnectivity, submitted to Forge through `/mobile/watch/actions:batch`, and reconciled through backend action receipts plus a refreshed watch snapshot.

People on watchOS is read-only and iPhone-relayed. Selection uses the existing owner-scoped Entity Navigation pins: the authenticated iPhone People UI deliberately pins or unpins a Person, preserves unrelated pins, and chooses the newest eligible active visible Person with an active peer relationship. Deleted, binned, revoked, invisible, cross-owner, and unpinned People are excluded with deterministic fallback to the next eligible pin or a neutral chooser state. The unlocked active watch may show the Person name, snapshot freshness, last connectivity, and a future event only when Forge explicitly provides it for sharing. Every locked, wrist-down, Always-On, notification, screenshot-fixture, or inactive presentation must remove the name, connectivity, and event. No Watch action may accept a relationship, widen a grant, approve or remove a device, revoke identity state, or mutate the pin.

Native People access must fail closed until the authenticated human explicitly enrolls the iPhone through a server-issued `forge-peer-companion-enrollment/v2` challenge. The device key is P-256 in the Secure Enclave with `WhenUnlockedThisDeviceOnly`, private-key-usage, and user-presence access control; private key material is never exported. Enrollment options and verification travel through the authenticated Forge web cookie transport, never through a pairing-token assertion. The signed proof binds the enrollment attempt, challenge, owner, pairing session, device id, public key, algorithm, protection, issue time, and expiry. Accepted receipts must advertise exactly the v2 enrollment, request, and consent protocols, the native People scopes and executable route set, and must prove that the legacy People bootstrap credential is disabled. Every later request signature and human-consent signature is produced by that same user-presence-gated key and contains no caller-selected `authenticatedAt` field.

Inbox must remain one coherent native surface. Its bootstrap payload includes existing watch prompts and an optional backward-compatible Attention summary with counts and at most three current items. The watch presents the summary and items as dense carousel cards without adding a second navigation destination, while the iPhone companion shows the count and first item in the existing paired menu. Source resolution and Attention actions remain owned by the Forge runtime and web experience.

The iPhone-watch bridge must publish real backend-backed snapshots for valid pairings, including older pairings that do not yet advertise `watch-ready`. It must keep the last good snapshot until a better one arrives rather than replacing it with an empty state while waiting for pairing or reachability. Psyche cards on the watch must be driven by Forge's actual Psyche definitions and recent reports; captured watch emotions, routines, moments, and triggers must become canonical Forge observations or trigger reports through the backend action path.

The movement life timeline must present stays, trips, sleep overlays, manual corrections, box invalidation, location labeling, and detail drill-down in a way that works cleanly on both desktop-class simulator layouts and real iPhone touch input. Visible buttons must have matching hit targets, and modal or sidecar movement actions must never be obscured by an overlapping transparent interaction layer.

The release contract for this subtree is explicit. Changes to the companion must preserve the live Xcode project, avoid casual project regeneration, build successfully through `xcodebuild` against the canonical simulator target, and remain compatible with the Fastlane-driven `testflight_release` path used by the repo’s local and tag-driven shipping flows. GitHub-hosted releases must sign with imported Apple Distribution assets and matching provisioning profiles for every shipped bundle id; the release architecture must not depend on Xcode-managed automatic signing minting fresh Apple Development certificates on ephemeral runners.
