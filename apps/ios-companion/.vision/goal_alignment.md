# Forge iOS Companion — Goal Alignment

Forge iOS Companion is the native Apple-device capture and sync client for Forge. It exists to bridge phone and watch sensors, permissions, background delivery, and lightweight user actions into the canonical Forge runtime without forcing the user to live in the web UI for every movement, health, or habit event.

The companion should feel native where the platform matters and subordinate where Forge already owns the domain truth. Pairing, permission prompts, movement capture, sleep and workout ingestion, watch relay, background sync, and small corrective actions belong in the app. Long-form planning, deep project management, and the broader Forge knowledge surface still belong to the paired Forge runtime.

The movement timeline is a particularly sensitive surface in this client. It must let the user inspect stays and trips, correct automatic movement boxes, label locations, and open detail views with reliable touch behavior on iPhone hardware. A timeline card that visibly presents actions but fails to register taps is a product bug, not a cosmetic issue, because it blocks the user from correcting canonical movement data.

HealthKit backfills are also a sensitive native surface. Large workout histories must not feel stuck in foreground-only tiny uploads: the app should batch and compress resumable chunks, show live upload counts and logs, and use the finite iOS background execution window to continue an active manual sync after the user leaves the app.

Agent Messages is the companion's native asynchronous owner-to-agent mailbox, not real-time chat. Tapping **Talk to agent** starts recording immediately when permission allows and presents a compact text composer plus default-or-selected connected-agent routing. Text, one original voice Artifact, or both must be sealed into an AES-GCM outbox before network delivery, with stable reservation and message identities surviving interruption and relaunch. Inbox, outbox, status filtering, box-specific opaque cursor pagination, complete forwarding/retry chains, mark-read, and generic notifications must remain owner-scoped. Outbox order follows immutable delivery; Inbox order follows newest unread eligible agent activity through a frozen traversal horizon, excluding claim and lease events. The app may retry in the foreground, on connectivity recovery, or during iOS-granted `BackgroundTasks` time, but it must never promise when Apple will run the task or write a persistent plaintext audio staging file.

The production stack for this project is explicit and binding: Swift 5 with SwiftUI for the iPhone and watchOS UI, MapKit for timeline maps, Core Location for movement capture, HealthKit for sleep and workout ingestion, BackgroundTasks for scheduled sync, WatchConnectivity for iPhone-watch transport, AVFoundation for capture, CryptoKit AES-GCM for the Agent Messages outbox, Keychain for its device-only key, a repo-owned Rust static library for the Forge Iroh/QUIC companion transport exposed to Swift through FFI, WebKit-backed embedding for the paired Forge web surface, Xcode project management through the live `ForgeCompanion.xcodeproj`, and Fastlane-based TestFlight and App Store release automation. The hosted CI release path is part of that production stack: GitHub Actions must import persistent Apple Distribution signing assets and matching provisioning profiles rather than depending on Xcode-managed automatic signing on ephemeral runners.

The architecture should remain local-first on device and Forge-first at the product level. The iPhone app owns credentials, sync retries, queued watch actions, and native capture state. The watch is a wrist-first Forge command surface: compact snapshots of work, habits, goals, today, health, movement, psyche prompts, inbox, and sync state are selected with the Digital Crown; horizontal card navigation selects subcomponents; all mutations flow through idempotent command receipts relayed by WatchConnectivity through the iPhone. Canonical Forge entities, movement projections, health evidence, task runs, and broader planning data remain anchored in the paired Forge backend. The bridge should preserve the last good watch snapshot and refresh it for any valid mobile pairing, including legacy pairings without a newer `watch-ready` capability, so the watch never degrades to empty pages simply because capability metadata is stale.

The existing Inbox surface also carries a bounded, read-only Attention summary from the paired runtime: active, important, and blocking counts plus a few current items. The iPhone companion may surface that compact summary in its existing menu, and the watch may show it beside watch prompts, but neither native client invents Attention records or bypasses the backend's actor scope and source rules.

People follows a stricter native boundary. An authenticated human may use the iPhone People relationship UI to add or remove the existing owner-scoped Entity Navigation Person pin. The iPhone selects the newest eligible visible Person pin with an active peer relationship and relays one compact snapshot to the watch. The watch may display that Person only while unlocked and active; locked, dimmed, Always-On, notification, screenshot-fixture, and inactive states expose only the Forge People title and a non-sensitive indicator. The watch never accepts relationships, changes grants, manages devices or identity, or creates a People-specific pin model.

People companion authority also requires a distinct explicit enrollment. A legacy pairing token must never enroll or authenticate a People device. Enrollment runs only through the authenticated human web-operator session, binds the owner, pairing session, device id, and public key to a short-lived server challenge, and completes only after a per-device Secure Enclave P-256 key signs with `SecAccessControl` user presence. Subsequent People requests and approvals use only that registered key and server enrollment identifiers; they never trust caller-selected authentication timestamps, raw private key bytes, or a separate UI-only LocalAuthentication result. The server must atomically disable the legacy People bootstrap path before the iPhone accepts and stores the enrollment receipt.
